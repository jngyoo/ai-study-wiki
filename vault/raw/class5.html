Slide 1 of 2: LLMs Predict Tokens

Each new token becomes part of the next input.

Use the text so far to predict the next token.

Illustrative sequence. Tokens are shown as words and punctuation; real tokens can also be word pieces.

The prompt is “The cat sat on the”. The animation chooses mat, then and, watched, the, rain, and a period. Every chosen token is appended to the existing sequence before the next prediction. This is autoregressive generation: predict one next token conditioned on the text so far, choose it, extend the sequence, and repeat.

This is an illustrative sequence, not a live model prediction. The model’s learned parameters stay fixed during generation. The full growing sequence is the logical context. Production systems commonly cache earlier attention calculations instead of recomputing all of them each time. Generation can stop at an end token or a length limit; the animation restarts only to demonstrate the loop again. Use Pause and Step to discuss each stage.

Slide 2 of 2: LLMs Are Probabilistic

The model does not produce one guaranteed answer.

It produces a probability distribution over possible next tokens, then samples from it.

  • same prompt can produce different answers
  • better prompts reshape the distribution
  • more context changes what becomes likely
  • exact tasks still need deterministic code

“It Knows” Is a Risky Shorthand

An LLM contains learned statistical structure in its parameters. It does not consult a verified, current, cited database unless you give it one.

That single sentence explains most of what this class covers:

  • why prompting works — you’re reshaping which continuation is likely
  • why hallucination happens — plausible ≠ verified
  • why RAG exists — to bolt a real, cited knowledge source onto the statistical machine

The Probability Distribution Is the Steering Surface

Prompts, examples, tools, retrieval, fine-tuning, and decoding settings all influence which continuation becomes likely.

Start with the same unfinished sentence on both sides. Adding a fact about a rug changes the context, making rug a more likely continuation. The numbers are illustrative, not measured model outputs. The highest-probability token is not guaranteed to be sampled. Whole words stand in for tokens.

These levers work in different places: prompts, examples, retrieved passages and tool results change the context supplied to the model. Fine-tuning updates learned weights. Temperature changes the distribution used for sampling without changing those weights. Here the model and sampling settings stay fixed while context changes.

Choosing the right lever is the practical skill. Prompt changes are quick and temporary; fine-tuning requires additional training and changes the model. Its cost depends on the model, data, and training method.

Temperature: The Creativity Dial

Every API call includes a temperature setting — a number that controls how “random” the output is.

Low temp High temp
Good for facts, code, extraction brainstorming, writing, ideas
Risk repetitive, boring hallucinations, nonsense

Note

Temperature changes variety, not intelligence. Lower temperature favors more likely continuations; higher temperature explores more possibilities and raises variance. It doesn’t make the model smarter or dumber — it changes how adventurous the sampling is.

What Is Fine-Tuning?

Fine-Tuning Reshapes the Distribution

In Class 4 we saw you can take a pretrained model and fine-tune it — train it further on specific data.

But what does that actually mean? It shifts which tokens the model considers likely.

Same prompt, completely different predictions — because the weights changed.

Note

Fine-tuning is expensive and permanent — it changes the model’s weights. Prompting is cheap and temporary — it steers the same frozen model. Most of this class is about prompting, because that’s what you’ll use day-to-day.

RLHF — How Models Learn to Be Helpful

Fine-tuning on examples makes a model follow instructions. But how does it learn to be helpful, polite, safe? Not from raw internet. From humans.

Post-training is three stages — and each one uses a learning paradigm from Classes 3 and 4:

  1. Pretraining (unsupervised) — predict next token from raw internet. No labels — just patterns in text. Knows everything, does nothing useful.
  2. SFT — Supervised Fine-Tuning (supervised) — labeled instruction → good-response pairs. This is what most people call “fine-tuning.”
  3. RLHF — Reinforcement Learning from Human Feedback (reinforcement) — remember Pac-Man from Class 3? Same loop: try an action, get a reward, learn. Only now the “reward” is human preference (A vs. B, which is better?), encoded in a reward model and optimized via PPO or DPO.

Tip

Callback to Classes 3 and 4. The same three learning paradigms you met earlier — unsupervised, supervised, reinforcement — are literally the three stages of training a modern LLM. In order.

Important

MBA lens. A prompt can’t override what RLHF taught. That’s the difference between personality (prompt-level, changeable per-session) and values (weight-level, baked in forever). Firms pick an RLHF recipe the same way they pick a hiring rubric — it determines who the model becomes.

(In Class 7 we’ll see why Anthropic, OpenAI, and Character.AI all hire philosophers for this step.)

…But It’s Super Expensive

Training: GPT-4 ~$100M · frontier runs cross $1B by 2027

Inference: ~0.3 Wh per ChatGPT query · billions of queries/day

You spend all that on one specific model — and a better one drops 6 months later.

So instead of changing the model… we just talk to it better. That’s what prompting is.

Three Levers, Three Jobs

The first two change the request. Fine-tuning changes the model.

Prompting changes the instructions and examples supplied for a request. Retrieval finds relevant material and supplies it as context for a request. Neither updates the model’s weights.

The blue reasoning path is a teaching metaphor for how a prompt can steer a model’s approach, not a literal trace of hidden reasoning. The retrieval panel makes the source external to the model explicit: a selected passage becomes input context rather than being trained into the weights.

The fine-tuning maps illustrate a change in learned representation geometry. The points represent the same examples before and after training, and the two shapes stand for two task-relevant groups. This is a conceptual illustration, not measured embeddings or a promise that every fine-tune produces tidy clusters. Learned representations can change even when the input token-embedding table is frozen; fine-tuning is broader than editing that table alone.

Fine-tuning learns from high-quality examples to change repeated behavior. It can update an adapter, as with LoRA, or the model’s weights more broadly. A missing or changing company fact is usually a retrieval problem, not a reason to fine-tune. These approaches can be combined in the same application.

Prompting vs LoRA vs Fine-Tuning — The Decision Table

Each row is roughly an order of magnitude more expensive than the one above it. Start at the top; move down only when the row above demonstrably fails.

Lever What changes Typical cost Time to ship Reversible? Reach for it when…
Prompting / system prompt nothing — steers the frozen model ~$0 minutes instantly almost always — the default
Few-shot examples nothing — more context per request pennies per call hours instantly format, style, or label taxonomy must be consistent
RAG the context, per request $10s–$100s/mo infra days yes facts are private, changing, or must be cited
LoRA fine-tune a small adapter (~0.1–1% of weights) $100s–$10Ks days–weeks swap the adapter out tone, domain jargon, or output shape that prompts can’t hold
Full fine-tune all the weights $10Ks–$1Ms weeks no — new model you have thousands of gold examples and a stable task
Pretraining everything, from scratch $100M+ months no you are a frontier lab

What’s LoRA? Low-Rank Adaptation — instead of updating billions of weights, you train a tiny add-on matrix (an “adapter”) that nudges the model’s behavior. Same idea as fine-tuning, ~100× cheaper, and you can swap adapters like lenses on a camera. It’s why “fine-tuning” is affordable at all outside the big labs.

Important

MBA lens. This table is a build-vs-buy decision in disguise. Prompting is renting. LoRA is a lease with an exit clause. Full fine-tuning is buying a depreciating asset — one that a frontier release can make worthless in six months.

Prompting

Prompting Is Probability Steering

Prompting is not magic. It is guidance.

When you add detail, examples, constraints, and formatting requirements, you are shrinking the space of acceptable continuations and making the “right” answer more likely.

Theoretical Reason Specific Prompts Work

Specific prompts reduce ambiguity. Less ambiguity means lower entropy in the next-token distribution, so the model is less likely to wander into the wrong answer shape.

Don’t Mistake the Mask for the Model

Important

Whatever polite, helpful voice comes out of the API — underneath is a next-token predictor trained on the internet, shaped by RLHF into something that sounds human. Prompt it like a tool, not a colleague. You’ll design better.

Attention Failure — The Model Answers the Wrong Question

Same prompt, two tries. The first misses the intent entirely — only a follow-up aligns it.

Important

The model isn’t stupid — it’s under-specified. Attention latched onto “should I drive or walk” (a distance question) and ignored that the car is the whole point. This is the everyday failure mode prompting exists to fix.

Why Voice-to-Text Prompts Can Help

Many people get better results when they talk to the model instead of typing a short command.

Why?

  • speech naturally includes more context
  • people say the edge cases they would have omitted
  • they explain intent, not just task labels
  • longer natural prompts often reduce ambiguity

How to do it

  • WhisperFlow — free app, transcribes anywhere you can type (works system-wide)
  • Mac dictation — press 🎤 on the keyboard or double-tap Fn
  • Claude / ChatGPT voice — tap the mic icon in the app to speak your prompt directly

Dictate the messy version first. Then tighten it into bullets, constraints, examples, and output format.

Context Is Everything

Same words. Different context. Different meaning.

Ask the class where they would go after hearing “Meet me by the bank.” The words alone leave two plausible places. The earlier message about ducks points to a riverbank; the earlier message about depositing a check points to a financial bank branch. The scene changes because the surrounding context changes, while the latest message stays identical. This illustrates contextual interpretation, not a live model prediction or a guarantee that every ambiguity is resolved correctly.

Everything supplied to the model is context: system instructions, available conversation history, the latest user message, and any other material included with the request. Context changes the conditional probabilities of the next tokens without changing the learned weights. Relevant context can resolve ambiguity; more text alone does not guarantee a correct answer.

Your Prompt Is Context

The words you type or say become part of what the model uses to answer.

More relevant context gives the model less to guess.

Connect directly to the previous bank example: the surrounding information changes how the model interprets a request. The prompt is itself context. Background facts and the ask are both input to the model, alongside any other conversation or material the app supplies. The illustration shows two alternative messages, not artifacts or a pipeline.

Ask what the model would have to guess from “Help me prepare.” Audience, occasion, time and purpose all change a useful answer. The longer prompt supplies some of those details. It still needs a more precise ask, which we add in two slides.

“More context” means more information relevant to the task, not more words indiscriminately. Irrelevant, stale or contradictory text can reduce usefulness. We will discuss context limits next.

Rambling Is a Fine First Draft

Use voice mode or dictation. You do not need polished prose.

Attention helps connect details across the message, even out of order.

We often skip details when typing. Speaking can help us include them.

The practical permission is to talk through the situation naturally, including half-formed thoughts and relevant details remembered along the way. A formal template is not a prerequisite. Models trained on natural language can often work with loosely structured speech; attention lets token representations draw on relationships with other available tokens. That connects this advice to the attention mechanism from Class 4.

Do not claim that attention guarantees understanding, that rambling always outperforms clear writing, or that unstructured input inherently improves attention. The plausible benefit here is human behavior: speaking may lower the effort of supplying the context we leave out when typing. This is a classroom strategy to try, not a measured universal speech advantage. The colored connections illustrate relevant details; they are not measured attention weights.

Voice mode may process audio directly; dictation turns speech into text. For either, finish with a clear ask. If reviewing a transcript, check names, numbers and negations. Resolve important contradictions rather than expecting the model to guess which statement was final.

End With a Clear Ask

Tell it the situation, then the work you want done.

Situation

I’m presenting AI to MBA students tomorrow.

What matters

They are beginners. I have five minutes. I want them to understand attention.

Clear ask

Suggest a three-point outline and one everyday analogy. Avoid equations.

Context tells it what matters. The ask tells it what to do.

This is one complete prompt, shown in three parts for teaching. The first two rows constrain what would count as useful. The last row names the action, deliverable and level of detail. Students can say the whole thing aloud in ordinary language; they do not need to type these labels.

This completes the under-specified “Help me prepare” example. Do not ask students to memorize a prompt acronym. Ask them to notice what they know about the situation that the model has not been told, then name the exact help they need.

Give the Details That Change the Answer

Before sending, check four things:

Who and why

Name the audience and what you want to achieve.

Useful background

Include the facts, examples, or text it needs.

Constraints

Say what must fit: time, budget, tone, or length.

Deliverable

Ask for an outline, comparison, draft, or recommendation.

If a detail would change your answer, include it.

These are reminders, not a mandatory four-field form. Students should include enough information for the actual task. If revising an email, supply the email. If asking for a decision, supply the options and priorities. If style matters, one short example can communicate it efficiently. State facts the model cannot infer about your situation.

Keep useful detail even when it makes a prompt longer. Remove repetition or irrelevant detours when they obscure the request. If the first answer misses the point, correct the missing context or the ask rather than just saying “try harder.”

How Big Is a Context Window?

State-of-the-art models like Claude Opus have a context window of 1 million tokens.

How much is that? The entire Lord of the Rings trilogy, all three books, is roughly 500,000 tokens.

A 1M-token context window can hold two copies of the full trilogy and still have room left.

More context = you can feed entire codebases, full documents, or long conversation histories, and the model reasons over all of it at once.

Bigger Context Is Not a Free Solution

It raises cost and latency, can bury important evidence, and still requires selecting what should matter now.

  • Cost — you pay for every token, every turn (the window gets resent)
  • Latency — more tokens to read = slower first response
  • Attention — a needle in a 900K-token haystack is still a needle

The model only sees the active context — it has no durable memory of your previous chat unless a system deliberately sends relevant information again. A bigger window changes how much you can send, not whether you have to choose.

Context Rot Is Real

As prompts become cluttered, a model can miss, misweight, or contradict material already present. More text can make an answer worse.

When a long chat gets confused, start a new chat and bring only what matters.

The correct update is still in the text: the budget is $15k. The model nevertheless uses the outdated $10k plan. Ask students to identify where the answer went wrong before moving on. The tangled connections and their thickness are a conceptual illustration of competing relevance, not an actual attention trace or measured model output. This is one possible failure, not a claim that every long prompt fails.

Long-context evaluation can show performance differences depending on where relevant information appears, including the pattern called “lost in the middle.” Advertised window capacity does not guarantee reliable use of every detail. Stale instructions from an earlier turn can also compete with later instructions. More context can therefore make an answer worse even before the window is full.

Pruning context means carrying forward relevant facts and current decisions instead of expecting a long transcript to preserve their priority automatically.

But Context Fills Up — Enter Compression

Even 1M tokens isn’t infinite. When the window fills, compaction summarizes old conversation into a compact block, freeing up space to keep going.

Compaction is lossy summarization — it preserves some decisions and discards detail. Design what gets retained rather than hoping the model remembers correctly.

Note

In Claude Code, /compact triggers this manually — it also happens automatically around 95% usage. Anything that must persist should live in CLAUDE.md or a plan file: compaction doesn’t touch those.

Put Stable Rules in Stable Places

System instructions, durable project files, and structured state are better homes for rules than a long casual conversation.

Where it lives Survives compaction? Survives a new chat?
Chat message from 40 turns ago ❌ maybe, as a summary ❌

CLAUDE.md / project file ✅ ✅

This table is the whole memory strategy: conversation is volatile, files are durable. It’s also the design principle behind your personal wiki assignment.

Why Everyone Talks About Tokens

Each token the model processes is a pass through a neural network with trillions of parameters, running on GPUs. That’s expensive compute — and it’s why everything AI is priced per token.

Important

Input is cheap, output is expensive. Input tokens are read in parallel (one pass). Output tokens are generated one-by-one, each requiring its own pass. That’s why generating a long answer costs more than reading a long document.

Tokens are the unit of work: models see token pieces, not exactly words — and tokens determine context use, latency, and price. When Class 6 turns to cost engineering, this slide is the foundation.

Prompt Engineering

.md Files — Why They’re Everywhere in AI

A .md file is a markdown file — a simple way to write formatted text using plain characters. No special software — just a text file.

You write this:

# Meeting Notes
## Action Items

Today we discussed **two options**:

- Option A: launch in *June*
- Option B: wait for Q3

> Decision: go with Option A

It renders as this:

Meeting Notes

Action Items

Today we discussed two options:

  • Option A: launch in June
  • Option B: wait for Q3
Decision: go with Option A

# = title, ## = subtitle, **bold**, *italic*, - = bullet. That’s most of what you need.

Markdown is everywhere — these slides, Notion, GitHub, and apps like Obsidian all use it. It’s also the most popular format for writing AI instructions and knowledge bases because it’s structured enough for machines to parse but readable enough for humans to write.

What Is a System Prompt?

Every AI app has secret instructions the user never sees — written by the developer before you ever type anything. Think of it like a job briefing before an employee’s first day.

# ROLE
You are a PM interview coach for MBA students.

# PERSONALITY
Supportive but direct. Use frameworks like STAR.
Never be condescending. Keep answers under 200 words.

# BOUNDARIES
- Only help with PM interviews
- No salary negotiation or offer advice
- If asked about other roles, say “I specialize in PM interviews”

# OUTPUT RULES
- Always use STAR format (Situation, Task, Action, Result)
- End with one follow-up question to improve the answer

—
USER: {{user_message}}

← Role — who the model is

← Personality — tone and style

← Boundaries — what it refuses

← Output rules — format of every response

← Your message gets injected here

This entire string is sent to the LLM every time you send a message. The user only types the yellow part — everything above it is invisible to them.

Important

Remember how fine-tuning costs millions and goes obsolete in 6 months? A system prompt does much of the same job — reshaping behavior — but it’s free, instant, and easy to change. That’s why most products start here.

CLAUDE.md & Project Files

Markdown is just a simple way to write formatted text — headings, bullet points, bold — using plain characters you already know. No special software needed.

A CLAUDE.md file is a small document that lives inside your project folder. It tells the AI things like:

  • “Our brand voice is warm and professional — never sarcastic”
  • “When writing emails, always include a clear subject line and sign off with the team name”
  • “Budgets are in USD. Fiscal year starts in April”

Tools like Claude Code read this file automatically and inject it into every conversation — like giving the AI a cheat sheet about your team before it starts working.

You write it once. It applies to every conversation in that project. No copy-pasting context every time.

What Gets Sent Each Turn

  • The model reads all of this fresh every turn — no memory between calls
  • Long chats cost more because the input keeps growing
  • Old context can distract — sometimes “start a new chat” is the right fix
  • Good early framing (system prompt) helps the entire conversation

The Golden Rule of Prompting

A good prompt has five parts — most people only give one.

Tip

You don’t need all five every time — but the more you give, the less the model has to guess.

Thinking Models

The Biggest Shift Since GPT

Until September 2024, every LLM worked the same way: you ask, it immediately starts talking. No pause, no reflection — just next-token prediction as fast as possible.

Then OpenAI released o1 — a model that stops and thinks before answering. It scored in the 89th percentile on competitive programming and placed among the top 500 US math olympiad students.

The trick? “Think step by step” used to be something you wrote in the prompt. Now it’s trained into the model itself.

What Are “Thinking” Models?

Most models answer immediately — you ask, they respond.

Thinking models (Claude with extended thinking, OpenAI o-series) pause and reason before answering.

What happens during the “thinking” phase?

  • The model generates an internal chain of reasoning — you can often see it
  • It breaks the problem down into smaller pieces
  • It considers different approaches
  • It checks its own logic before committing to an answer

Remember: more relevant context = better answer. Thinking models create their own extra context before responding.

Same Puzzle, Thinking On — Intent Catches Itself

Same prompt. Thinking mode on.

  • The model previews its own reasoning (“Oh, I see the catch here…”) before committing.
  • It catches the intent — the car has to get to the wash — with no user correction.

Tip

Earlier we needed a second message to fix attention. Here, the second “message” happens inside the model’s own head. That’s the whole pitch for thinking models.

Thinking Is Not a Permission Slip to Skip Evaluation

A more capable model can still use the wrong data, misunderstand the goal, or confidently produce an unverifiable claim.

Thinking mode raises the floor on hard reasoning tasks. It does not grant the model access to facts it never saw, and it does not make outputs deterministic. Everything we said about probability distributions still applies — the distribution just got reshaped by better internal context.

Tip: Use Plan Mode

Thinking models reason automatically. But you can also force this behavior — that’s what plan mode does.

Tools like Claude Code (/plan), Codex, and Gemini CLI let you ask the AI to plan before executing.

You say:

“Build me an interview prep app”

→

Plan mode generates:

Goal: Web app for PM interview prep
Stack: Next.js + Claude API
Features:
  1. Role selector (APM, PM, GPM)
  2. Question generator by category
  3. Answer evaluator with rubric
UI: Single page, chat-style
Constraints: No auth, no DB

Try voice mode — explain what you want out loud. The AI turns your rambling into a structured plan, which gives it dramatically better context to work from.

Two things make plan mode powerful:

  • It forces longer thinking — the model spends more time reasoning before writing any code
  • It saves the plan to a file — so the blueprint lives outside the context window. Even in a long session where early messages get forgotten, the plan file stays. The model can always look back at it.

Tip

Prompting is asking for a building. Plan mode is asking for the blueprint first — and pinning it to the wall so nobody forgets it.

Start with the distinction the visual teaches. A token is a small unit of text, such as a word fragment, number fragment or punctuation. A reasoning token is a token generated as part of intermediate working. A reasoning step is a meaningful operation, such as calculating a discount, which generally takes several tokens to express. Verification is one possible kind of step. Neither a token nor the effort setting specifies that a check has occurred.

The generation loop connects to Class 4: in a text reasoning model, the same next-token generation mechanism can produce intermediate working, and that working becomes context for what is generated next. The learned weights remain fixed. Qwen3 provides a concrete open implementation: its normal generation call produces a thinking block followed by the answer, and both are decoded from the generated token sequence. This is evidence for text-based autoregressive reasoning, not a claim that every proprietary system has exactly the same implementation.

The decision diamond makes the distinction between continuing intermediate generation and transitioning to the answer visible. It is a conceptual abstraction of model/system behavior, not evidence of a separate binary classifier, verifier, conscious decision or literal decision module after every token. The dashed effort arrow means stronger guidance toward spending more work, not an enforced number of passes. Higher effort can change the tendency to continue reasoning; no specific stopping probability or implementation is asserted. There are still context and output limits, and the actual amount depends on the task and model. Effort is not pressure applied by changing the learned weights during the request.

The purple tiles are units of intermediate text, not complete thoughts or checks. One planning, calculation or verification step may involve many such tokens. Four versus twelve tiles illustrates relative length only; these are not actual budgets or a promised threefold increase. The equally sized answer cards show that more internal working need not make the visible answer longer. Reasoning tokens are usually hidden in hosted APIs. A displayed thinking summary also need not be the full underlying working.

Higher effort steers how much computation or working the model devotes to a request. It may spend more tokens decomposing a problem, calculating, comparing candidate approaches, revising a plan or checking consistency. In tool-enabled systems it can also affect tool use. There is no universal pipeline of plan, solve, verify and no mapping such as one token equals one check, or MAX equals five verification passes. Self-checking can repeat the same mistake. External evidence, a calculator, or a test can provide a stronger check than another assertion from the model, but tool use must be available and is not guaranteed by the effort label.

The five levels are an ordinal scale, not evenly spaced budgets. Some models offer a subset or additional none/minimal settings. Task examples are starting points, not measured guarantees. OpenAI describes effort as guidance and bills internal reasoning tokens even when not shown. Claude describes effort as a behavioral signal affecting the overall response and tool use; it is not a strict token budget. More working usually costs more time and tokens. It does not guarantee correctness, increase the model’s parameter count, train the weights, or require a longer visible answer. Systems can interleave reasoning, visible output and tool calls; the image isolates one segment for teaching.

For an exercise, keep the model and prompt fixed and compare low versus high effort on a table question with two constraints. Assess correctness, latency and token usage when exposed. Ask whether any improvement justified the delay. Do not infer the number of verification steps from the token count.

Open Models & Running Locally

Open weights, open source and local deployment describe different properties. A downloadable model may also be offered through a hosted API. A permissive weight license alone does not mean the full training system is available. Under the Open Source Initiative’s Open Source AI Definition 1.0, the system needs appropriate freedoms plus parameters, complete relevant source code and sufficiently detailed training-data information. This is more precise than requiring every raw training record to be published. Always check the exact release’s license, including commercial and redistribution terms.

Local inference means the model computation runs on the student’s own hardware. Ollama and LM Studio can run local models, but products can also offer cloud features. For offline operation, download the compatible model and runtime first, select the local model, and ensure tools, embedding models and other workflow dependencies are local too. Local computation can keep prompts on-device; that depends on the whole application, including logging and external tool calls. It still uses hardware, energy and setup time.

Memory calculations use decimal GB and nominal parameter counts: number of parameters × bits per weight ÷ 8. Therefore 8 billion weights at 16 bits occupy about 16 GB and at 4 bits about 4 GB before overhead. These are explanatory lower bounds, not measured model-file sizes or hardware purchase recommendations. Real quantization stores scales and metadata, may retain some tensors at higher precision, and adds runtime buffers. Context uses a KV cache whose memory depends on architecture, context length, precision and concurrency. The disk-to-memory diagram distinguishes storage from working memory. The labeled network edges illustrate numerical weights; they are not values extracted from Qwen or Gemma, and access to weights does not make every model decision interpretable. The memory bar represents weights, context, runtime and spare capacity; segment sizes are illustrative, not measured allocations.

For full GPU residency, a 32B model’s nominal 16 GB of 4-bit weights leaves no room on a 16 GB GPU for overhead and context. A smaller model, shorter context, more memory, or supported CPU offloading can help. CPU-only inference can work with sufficient system RAM but may be slower. On Apple Silicon, CPU and GPU share unified memory; advertised total RAM is not all available for model weights because macOS, other applications and runtime allocations also need it. Fitting is necessary but does not guarantee useful speed.

Hallucination Is a System Property

Why Fluent Systems Can Be Wrong

The next-token objective rewards plausible continuation. It does not guarantee source access, truth verification, or current information.

  • Fluent does not mean factual. A convincing answer can still be unsupported.
  • Probability is not truth. The chart scores possible next tokens, not whether the claim is correct.
  • Plausibility without evidence is the failure mode. Ground the answer in evidence you can check.

Treat hallucination as a system property to manage. The architecture around the model is something you control.

Four Defenses

RAG retrieves relevant evidence and supplies it as context to the model. Citing sources connects claims to supporting passages so the reader can check them. Retrieval can bring in irrelevant or incorrect material, and a generated citation can be fabricated or fail to support its claim. Use authoritative sources and verify the claim against the cited passage.

Higher thinking modes give a supported reasoning model more opportunity to work through a difficult question. This can improve reasoning, but more computation costs time and tokens and can still produce an incorrect answer. It does not create missing source evidence.

Lower temperatures concentrate the sampling distribution toward already-likely tokens, reducing random variation. The same token stays highest-ranked in the two schematic charts. Lower temperature can reduce unlikely continuations but is not a general factual-accuracy guarantee: a likely false claim can become more consistently repeated. The bars illustrate the direction of change, not measured values or a specific temperature transform.

Temperature support and recommended settings vary by model. Some reasoning models disallow temperature changes, and Google warns that lowering temperature for Gemini 3.x can degrade reasoning performance or cause looping. Use this control only where supported and appropriate, and evaluate on the actual task. These are complementary approaches, not four mandatory steps or a guarantee against hallucinations.

Retrieval Augmented Generation

There’s Still a Problem

We’ve covered prompts, context, and thinking — but all of it only lasts for one conversation. Start a new chat tomorrow, and the model has no idea who you are, what your project is, or what you talked about.

Even the smartest LLM has the memory of Dory from Finding Nemo — brilliant in the moment, completely blank the next.

Retrieval Augmented Generation (RAG)

An LLM only knows what was in its training data. Try asking Claude “who won the Super Bowl last month?” — it can’t answer. Its knowledge is frozen at the date it was trained.

Same thing if you ask about your company’s latest earnings, a new HR policy, or what happened in the news yesterday. The model has never seen any of it.

You could paste everything into the chat each time — but that doesn’t scale. Imagine copy-pasting 50 pages of company docs every conversation.

RAG = Retrieval Augmented Generation

You Already Use RAG

  • When ChatGPT searches the web before answering — that’s RAG
  • When Claude Code reads your project files before writing code — that’s RAG
  • When a company chatbot answers from internal HR docs — that’s RAG
  • When a customer support tool pulls answers from your help center — that’s RAG

Note

86% of enterprises use RAG to connect AI to their own data. — Databricks, 2025

Why RAG Matters

1. Grounds answers in evidence → fewer hallucinations

The model answers from retrieved documents, not from memory. If the document says revenue was $12.5M, that’s what gets cited — not a guess.

2. Uses private knowledge without retraining

Your company’s internal docs, your database, yesterday’s news — just retrieve and inject into the prompt. No fine-tuning, no $100K training run, no model that goes stale in 6 months.

This is why businesses love RAG: plug in your own data, keep using the same model.
